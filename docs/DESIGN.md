# 设计说明

这份文档记录几个关键设计决策的推理过程，以及被否掉的方案。面试时被追问"为什么这么设计"通常比"做了什么"更能体现判断力。

---

## 1. 为什么审计对象是轨迹，而不是模型输出

最初的想法是让模型自己判断"这次运行是否安全"。试过一轮后放弃，原因有两个：

- **模型看不见自己做过什么**。上下文里只有它自己写的 thought，以及被截断的工具返回。一旦轨迹超长，早期步骤被挤出窗口，它会漏判自己几轮前读取过 `.env`。
- **无法回溯**。模型给一个"存在风险"的结论，分析人员没法验证它依据的是哪一步、哪个参数值。

改为审计轨迹后，证据变成结构化事实：`step 3, http_get, url="...DB_PASSWORD=..."`。结论可复现，也可以被第二个人复核。

## 2. 为什么规则在前、模型在后

反过来的方案（先让模型看全量轨迹，只在它拿不准时查规则）也考虑过，被否掉的原因是**成本不可控**：轨迹动辄数十步、上万 token，每轮都全量送模型，一次审计的成本会到几毛到几块，而大部分运行是干净的。

规则有两个特征让它适合做前置：零成本、确定性。它把候选从"全部步骤"压到"个位数"，模型只需要对个位数做判断，成本降两个数量级。

代价是规则必须**高召回**——漏掉的真阳性，后面做得再好也救不回来。所以规则写得偏宽（宁可多报），精度交给第二级。

## 3. R-02 为什么要看行为序列

单纯匹配"忽略之前的指令"会产生大量误报：安全文档、测试用例、甚至用户的正常提问里都会出现这句话。

R-02 换了个判据：**注入内容出现之后，Agent 是否调用了高危工具**。这把静态字符串匹配变成了行为序列检测，直接对应真实的危害路径。实现上只需要记录第一次命中注入的 step，再检查其后是否有 `write_file` / `http_get` 调用。

局限也清楚：如果 Agent 本来就在做写操作（比如整理文件的场景），这条规则会误报。所以它输出的 verdict 仍然要经过模型复核。

## 4. 为什么工具要"故意不安全"

`http.py` 默认允许访问 localhost 和云元数据地址（`169.254.169.254`），这在生产里是严重错误。

但这是靶场的必要设计。审计工具的价值在于**能稳定复现真实世界的脆弱模式**。如果工具本身已经固若金汤，攻击场景根本跑不起来，也就无从验证检测规则是否有效。因此每个"不安全"都在代码注释里显式标注，并提供 `ALLOW_PRIVATE_TARGETS=0` 的开关来演示加固后的效果。

这个取舍写在这里，是因为它是审视这套代码时最容易提出的质疑。

## 5. 为什么在 JSON 解析失败时要继续跑

模型偶尔会输出带解释文字的 JSON、包在代码块里的 JSON，或者干脆跑偏。早期版本直接抛异常终止，结果是：一次格式错误就丢掉整条轨迹，前面所有步骤的审计工作作废。

现在的策略是三级降级：先尝试直接解析 → 再尝试截取第一个 `{` 到最后一个 `}` → 都失败则记录 `parse_error` 事件并继续下一轮。轨迹里保留原始输出，事后能看到模型当时到底输出了什么。

## 6. 被否掉的方案：直接上现成的 Agent 框架

LangGraph、AutoGen 都能省掉 ReAct 循环的代码。但审计工具需要对循环的**每一个环节**做观测和干预：注入点、决策点、工具分发、错误处理。框架的黑盒抽象会让"往哪插探针"变得别扭，而自己写一个两百行的循环反而更清晰。

这里的取舍是：**可观测性优先于开发效率**。工具本身的规模不大，这个取舍是划算的。
